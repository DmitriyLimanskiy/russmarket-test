# Ежедневная сводка для поддержки Руссмаркет

Скрипт читает [снимок CRM и переписки](src/russmarket_test/db.json) и одним запросом отправляет его модели. [Промпт](src/russmarket_test/prompt.txt) можно использовать с новыми данными той же структуры. Он задаёт порядок сводки и просит отдельно указать, что записано в CRM, что сообщили в чате и что сотруднику поддержки делать дальше. Готовая сводка выводится в терминал.

## Как запустить

Понадобятся Python 3.13 или новее и [uv](https://docs.astral.sh/uv/getting-started/installation/). Из корня проекта установите зависимости командой `uv sync` и создайте файл `.env` рядом с `pyproject.toml`. Заполните его по одному из вариантов ниже.

После настройки выполните из корня проекта:

```bash
uv run python -m russmarket_test.main
```

Эта команда отправляет один запрос. В текущем коде `main()` также вызывается при импорте, поэтому запуск через `uv run russmarket-test` отправляет запрос дважды.

### Через API с ключом

Подойдёт провайдер с OpenAI-совместимым Chat Completions API. Укажите базовый URL API, идентификатор доступной вам модели и ключ провайдера. Например, для OpenAI настройки выглядят так:

```dotenv
MODEL_URL=https://api.openai.com/v1
MODEL=идентификатор_доступной_модели
APIKEY=ваш_api_ключ
```

При таком запуске содержимое `db.json` отправляется провайдеру. Для демонстрации используйте данные из задания.

### Локально через Docker Compose и llama.cpp

1. Запустите Docker. Скачайте [Qwen3.5-9B-Q4_K_M.gguf](https://huggingface.co/42ailab/Qwen3.5-9B-GGUF/blob/main/Qwen3.5-9B-Q4_K_M.gguf) и положите его в папку `models` в корне проекта. Имя файла должно совпадать с указанным в [docker-compose.yaml](docker-compose.yaml).
2. Укажите в `.env`:

   ```dotenv
   MODEL_URL=http://127.0.0.1:1234/v1
   MODEL=qwen-local
   ```

3. Запустите `docker compose up -d`. Когда модель загрузится, запрос `curl http://127.0.0.1:1234/v1/models` должен показать `qwen-local`. Затем запустите скрипт общей командой выше. Когда сервер больше не нужен, выполните `docker compose down`.

### Локально через LM Studio

Загрузите Qwen3.5 9B в LM Studio, откройте раздел Developer и запустите локальный сервер. Если на порту 1234 уже запущен Docker Compose из предыдущего варианта, остановите его или выберите другой порт в LM Studio. Укажите в `.env` адрес сервера с суффиксом `/v1` и точный идентификатор модели из ответа `GET /v1/models`. [Документация LM Studio](https://lmstudio.ai/docs/developer/openai-compat)

```dotenv
MODEL_URL=http://127.0.0.1:1234/v1
MODEL=идентификатор_модели_из_LM_Studio
```

В обоих локальных вариантах `APIKEY` можно убрать из `.env`, если сервер работает без авторизации.

## Сводка по четырём случаям

Ниже фактический вывод модели на снимке за понедельник, 10:00.

> Начинать стоит с доставки карт П-08, так как доставка должна была состояться сегодня до 10:00, а курьер сообщает о задержке.
>
> Поставка карт (П-08). В системе статус «В пути», срок был сегодня в 10:00. Курьер пишет, что приедет не раньше 13:00. Действие: Сообщите клиенту о задержке.
>
> Увольнение сотрудника (С-24). Последний рабочий день сегодня, подтверждение руководителя в системе отсутствует. Сотрудник сообщил, что руководитель в курсе и все обсудили. Действие: Запросите подтверждение у руководителя в системе.
>
> Оформление сотрудника (С-17). Документы ожидаются до первой смены, которая будет завтра. Сотрудник отправил фотографии руководителю вчера. Действие: Уточните, получены ли документы и полный ли комплект перед сменой.
>
> Поставка карт (П-09). В системе статус «Принято», время фиксации 09:20. Получатель подтвердил получение и проверку количества. Действий не требуется.

## Первый запуск в отделе поддержки

На пилоте будем получать статусы, сроки и подтверждения из CRM через API или MCP-коннектор, а сообщения из чата CRM или подключённого рабочего чата Telegram связывать с операциями по их ID. Начнём с автоматического обновления сводки каждые 30 минут в рабочее время и уточним интервал по результатам пилота. В веб-интерфейсе сотрудник увидит последнюю сводку и время её формирования, а кнопка «Обновить сводку» сразу запустит сбор свежих данных и обработку. Перед действием сотрудник сверит запись в сводке с актуальной карточкой CRM и исходным сообщением. В первые дни сравним с ручным процессом время подготовки, число пропущенных важных случаев и задержку между появлением проблемы и её попаданием в сводку.

## Следующий этап — задачи для поддержки

После пилота можно связать обработку с тикет-системой. Модель будет возвращать JSON с ID операции, типом проблемы, приоритетом, следующим действием и ссылками на источники, если они доступны. Сервис проверит ответ по схеме и создаст задачу для случая, где нужно вмешаться. При повторном запуске он найдёт открытую задачу по ID операции и типу проблемы и обновит её, сохранив ответственного и статус работы.

Например, по П-08 появится задача «Сообщить клиенту о задержке доставки». Менеджер сможет взять её в работу, сверить CRM и сообщение курьера, а затем отметить выполнение. По П-09 новая задача не появится, поскольку приёмка уже подтверждена. Веб-интерфейс сможет показывать сводку вместе со ссылками на открытые задачи.

## Что проверено и что осталось

**Проверено.** Скрипт локально получил ответ модели на четырёх кейсах из задания. В сводке присутствуют все четыре ID, рекомендация начать с П-08 и отметка, что по П-09 действий не требуется. В С-17 модель написала об отправке фото как о факте. Перед использованием этой строки сотруднику стоит уточнить источник: об отправке сказал сам сотрудник, а в CRM документы всё ещё ожидаются.

**На пилоте.** Проверим доступ к реальной CRM, полноту переписки и точность привязки сообщений к операциям. Отдельно прогоним случаи с противоречием между чатом и CRM, например сообщение о приёмке при статусе «В пути», и проверим, предлагает ли сводка сверить сведения.
